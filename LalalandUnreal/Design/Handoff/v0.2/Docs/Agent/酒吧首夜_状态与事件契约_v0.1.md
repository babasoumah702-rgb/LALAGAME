# LaLa-Land｜酒吧首夜状态与事件契约 v0.1

> 2026-09-20，给 UE5 技术同学的接入设计，**不是已实现功能**。人物表达见[四人 Agent 提示词](酒吧首夜_四人Agent提示词_v0.1.md)，具体菜单见[酒单与饮品偏好](酒吧首夜_酒单与饮品偏好_v0.1.md)，体验范围见[首夜创作整稿](../酒吧首夜_创作整稿_v0.1.md)。本地 `UE5/LalalandUE`、`UE5/WansaiFastPath` 是角色／交互样板，尚未确认技术同学的 UE5 主工程路径。因此本文不改旧 Unity 服务端，也不声称新服务端已接入。

## 1. 先分清谁管什么

| 层 | 权威内容 | 不负责 |
| --- | --- | --- |
| 世界／玩法状态（服务端或可保存的游戏逻辑） | Cash、饮品价格与成分、实际付款和饮用、醉意阶段、投球物理结果、位置、可见事件、邀请答复、关系数值 | 不编人物台词 |
| 单角色固定卡 | 身份、工作、说话方式、偏好、边界、已确认的共同经历 | 不记录今夜 Cash、醉意、好感、玩家刚做过的事 |
| 单角色运行上下文 | 她**实际知道**的现场情况、自己的状态、对玩家的印象、她可见的近期记忆 | 不接收其他角色私密记忆或全局真相 |
| Agent 输出 | 在允许动作里提议行为和台词，并引用依据 | 不直接改 Cash、饮酒量、投球结果、关系值或“同意”标志 |
| 机会调度层（首版“天道”） | 在对话空档投递工作人员组局、赛后机会、流星雨提醒 | 不替角色决定爱谁、不随意发明事故或强制推进剧情 |

## 2. 最小状态模型

数值范围和饮品清单是原型调参项。以下 `intoxicationPoints` 是**虚构游戏单位**，不是酒精医学换算；不应用于现实饮酒建议。初版可只用 `sober / light / impaired` 三段，不必先做复杂生理模拟。

```json
{
  "night": {"phase": "free_time", "meteorWindow": "later", "gameStatus": "not_started"},
  "people": {
    "USER": {"cash": 18, "drinksConsumed": [], "intoxicationPoints": 0, "drinkStage": "sober", "feigningDrunk": false},
    "A": {"cash": 30, "drinksConsumed": [], "intoxicationPoints": 0, "drinkStage": "sober", "feigningDrunk": false}
  },
  "relations": {
    "A->USER": {"trust": 0.5, "closeness": 0.25, "attraction": 0.1, "safety": 0.6, "tension": 0.1, "uncertainty": 0.5}
  },
  "events": [],
  "invitations": []
}
```

- `cash` 只因成功交易而变化。`drinksConsumed` 只记**真正喝下**的饮品，不把下单、赠送、递杯或比赛入杯算成饮用。
- `drinkStage` 根据实际饮用、经过时间、角色原型参数计算，不由台词或角色自报覆盖。每位角色可以有不同的阶段阈值，但阈值需作为可调整游戏参数而非性格判断；不把职业、T 身份或性取向推成酒量。
- `feigningDrunk` 与真实醉意分开。其他角色不能直接读它，只能从可见动作推测。玩家假装醉能产生对话机会，也可能被识破；不能借此自动获得触碰或同行许可。
- `relations` 保留旧实现中可复用的六维含义：`trust` 信任、`closeness` 熟悉／亲近、`attraction` 浪漫吸引、`safety` 相处安全感、`tension` 紧张、`uncertainty` 不确定。**只复用状态维度，不继承旧版数值、人物纠纷或脚本。** 首夜新初值要逐人逐关系重设，陌生玩家默认无已建立恋爱关系。
- 即使六维数字达到阈值，邀请答复仍需检查角色意愿、当下身体状态、共同经历与是否尊重过拒绝；“一起看流星雨”可以是朋友同行。

### 第一轮“能喝多少”的原型参数【全部为提案】

仅用于让四人表现稍有差异、便于测试，**不声称是现实酒量，也不从职业、身份或体型推断**。假设无酒精饮品增加 `0` 点，菜单上的低度／常规酒精饮品分别增加 `1`／`2` 个**虚构游戏点**。达到第一阈值为 `light`，达到第二阈值为 `impaired`；低于第一阈值为 `sober`。调参时可以全部改掉。

| 角色 | 进入 `light` | 进入 `impaired` | 首轮表现提案 |
| --- | ---: | ---: | --- |
| 玩家 | 2 点 | 4 点 | 轻微微醺时可选择低强度视效；明显醉意时优先提示休息，不靠失控制造攻略机会 |
| Kiko | 1.5 点 | 3 点 | 先确认自己是否还想继续喝；说话稍慢，不突然失去边界 |
| X | 2 点 | 3.5 点 | 玩笑变少、表达更直；明显受影响则暂停需要认真承诺的对话 |
| 万塞 | 2 点 | 4 点 | 可能更爱回嘴；明显受影响则不再参加竞技或作亲密决定 |
| 一桐 | 1.5 点 | 3.5 点 | 反应和语速可变化；明显受影响则停杯、坐下或离开活动 |

四人可随时**主动停杯**，包括在阈值以下；阈值只决定系统表现，不规定“还能再喝几杯”。恢复节奏按游戏时间做保守、可解释的阶段变化，首轮不模拟现实代谢。不得用“喝到阈值”作为露台邀请的攻略任务。以上数值正式接入前需由创作者和试玩共同确认。

## 3. 饮品交易与反应的可验证顺序

1. **选择**：玩家自己点、给别人点或做特调；菜单给出名称、价格、风味、是否含酒精。比赛目标杯与饮用杯是两种道具。
2. **验价与来源**：检查 Cash、券是否有效、调制条件是否满足；不够钱则没有交易事件，不触发“请客成功”。
3. **询问意愿**：送给角色时先出现 `drink_offer`；角色可接受、拒绝或提出无酒精替代。拒绝只记为一次边界表达，不自动记成负面好感。
4. **交付与饮用分开**：成功购买／制作产生 `drink_served`；角色或玩家真正喝时才产生 `drink_consumed`。饮用可分口数，原型也可用一杯一次；不能仅因接受饮品就瞬间醉。
5. **状态更新**：程序计算 `drinkStage`，为第一人称视效发送状态；更新角色自己的可见状态。玩家画面渐变模糊必须能在设置中降低／关闭，且不妨碍读字、操作与安全提示。
6. **关系解释**：角色基于偏好、交流和边界对互动给出反应；关系层记录**有证据的互动**，不是“饮品 ID = 好感 +10”。一杯合口味的饮品可打开话题；连续灌酒或不尊重拒绝可降低安全感。

饮品口味与阶段表现采用[提示词稿](酒吧首夜_四人Agent提示词_v0.1.md)中的四人提案；其中“爱喝什么、能喝多少、喝后如何说话”须分成三件事：口味写进人物卡，实际喝下多少写进世界状态，临场表现通过状态输入给 Agent。绝不靠一段人物 prompt 代替事件记录。

## 4. 关系更新与玩家反馈

一次交互至少记录：`eventId / actor / target / action / drinkId? / witnessedBy / accepted? / consumed? / reasonTag`。关系变化要引用具体事件，不从角色的台词猜测“她似乎喜欢你”。例如“玩家记得 Kiko 明确说过不想再喝，改问她想不想看夜景”可以提高安全感；“玩家拿到特调券”本身不改变吸引值。

建议首版 UI 不显示精确六维数值，而显示玩家能理解的阶段与原因：`刚认识／聊得来／愿意单独相处`，加一条最近事实，如“她记得你尊重了她的拒绝”。身体状态可显示 `清醒／微醺／明显醉意`。这只是 UI 提案；后台保留数值便于调参与验收。若未来想显示“好感度”，须说明它是多维关系的概括，不能误导为已获得同意。

## 5. 酒吧主链路对接

| 触发 | 权威事件 | Agent 可做什么 |
| --- | --- | --- |
| 开场球滚来 | 球的位置与玩家是否拾取／试投 | 按亲见动作回应；不捡不扣分 |
| 工作人员到点组局 | 规则、参加者、奖惩提前公布 | 各自决定参加／旁观；不能替玩家报名 |
| 五人弹球入杯 | 实际球路、命中、赢家与末位 | 对真实输赢和赛后举动作不同反应；不能靠台词改比分 |
| 赛后彩头 | 券或轻任务到账、是否执行 | 对玩家如何使用奖品／处理失利作评价；奖品不买到约会 |
| 流星雨窗口 | 可观赏时间、露台状态 | 可主动邀请、以朋友同行、接受或拒绝；尊重重复拒绝 |
| 结算 | 本晚公开事件与各自亲见记忆 | 各写一句基于证据的感受；不知道的事不评价 |

## 6. 首轮验收（技术同学可直接跑）

- 玩家买饮品但没喝：Cash 减少，`drinksConsumed` 不变，画面不模糊；角色不能说“你喝多了”。
- 玩家送 Kiko 不合口味的高糖饮品，她拒绝：不扣强制好感、不消耗她的酒量；后续尊重拒绝仍可聊天。
- 玩家用券送万塞无酒精饮品：券消费一次，万塞可收或拒；她不因运动背景被强制接受或强制禁酒。
- 玩家装醉但实际没喝：本人真实阶段仍清醒；别人只根据可见行为判断。试图靠身体贴近仍需对方同意。
- 玩家和 X 私聊：站远的一桐不知道私聊内容，结算不能引用。
- 五人比赛胜负来自投球判定；输赢带来彩头／任务，不直接加浪漫值。
- 玩家无论是否成功邀请，都能独自上露台或结算；被拒后再连点邀请不刷出同意。
- 任一角色明显受影响时，不由系统推动亲密承诺；可休息、喝水、结束当晚对话。

## 7. 接入顺序与未决项

1. 请技术同学提供真正运行中的 UE5 主工程绝对路径及 Agent 服务端／提示词配置路径。本仓库样板不等于主工程；**未接入前不要在产品演示或对外材料称饮酒、Cash、关系系统已实现**。
2. 先接入一名角色＋一款酒精饮品／一款无酒精饮品，打通 `购买 → 接受／拒绝 → 实际饮用 → 状态变化 → 角色回应 → 保存/读取`；通过验收后再扩成四人。
3. 接入五人游戏与流星雨机会窗口，让奖惩和邀请基于真实事件；此后再讨论更开放的“天道”。
4. 创作者需确认四人的口味、游戏单位下的微醺阈值和明显醉意表现；阈值由试玩调优，不按现实酒量或身份标签硬推。
